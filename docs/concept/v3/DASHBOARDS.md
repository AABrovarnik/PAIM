# PAIM V3 — каталог дашбордов и пользовательские сценарии
Статус: DRAFT | 2026-11-25.
## 1. Интерфейс: один щелчок, запрос или подписка
Telegram — быстрые команды, диалог, ссылки и уведомления. Web — единый Personal Command Center, компактные карточки, фильтры и детализация. Не создавать полноценные редакторы приложений. По ссылке открыть оригинал, по запросу сформировать предложение изменения, но не отправлять без согласия.
Каждый дашборд имеет: период и timezone, момент формирования, freshness каждого источника, coverage (доступен/частично/недоступен), факты с источниками, выводы и рекомендации отдельно, кнопки обновить/детализировать/открыть источник. Кэш помечен временем; при ошибке показывать частичный результат, не нули вместо отсутствующих данных.

## 3. Шаблон ежедневного брифинга
1. Сегодняшняя дата, timezone, время обновления, покрытие источников.
2. Важные сроки и встречи, конфликты, обязательства, ожидаемые ответы.
3. До трех рекомендуемых результатов с причиной (цель/риск/срок), альтернативы при ограничении времени.
4. Реальная доступность времени: объединение busy интервалов, резерв 25% как предлагаемый default, неизвестные оценки отдельно. Не создавать временные блоки автоматически.
5. Материалы к встречам/задачам: до трех ссылок на актуальные документы RAG.
6. «Что требует решения»: противоречия, неизвестные сведения, недоступные источники.
7. Действия: открыть оригинал, обновить, отложить уведомление, согласовать предложение (write не входит в read-only пилот).

## 5. Проактивность
По умолчанию только согласованные подписки. Предлагаемые: утренний брифинг, вечерняя короткая рефлексия, недельный обзор и тематический дайджест. Месяц/квартал позже. Событийные уведомления только для явно заданных порогов важности/срока; группировка, quiet hours, snooze, выключение, объяснение причины. Не повторять уведомления при отсутствии изменения; очереди с idempotency и журналом. Владелец выбирает канал/время/тему; отсутствие доступного источника не означает отсутствие риска.
## 6. UX цель
Один экран и один диалог, не 12 отдельных приложений. В P0 несколько шаблонов переиспользуют общий компонент представления. Детальные настройки/редакторы остаются в исходных сервисах. Цель пилота — меньше переходов и повторного ввода, а не больше визуальных карточек.
